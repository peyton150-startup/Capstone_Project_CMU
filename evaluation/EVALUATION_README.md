# Evaluation workflow

> **Full-project readiness:** [CRITERIA_FOR_EVALUATOR.md](CRITERIA_FOR_EVALUATOR.md) defines the unresolved P0/P1 fixes, regression tests and staged acceptance gates. The scripts below describe the current scaffold; they do not establish that an end-to-end project evaluation is ready or calibrated.

How to produce the evidence, build the inventories and packets, prepare
Snap requests, read the results and compare experiments. Everything here
runs offline except the optional `--send`, which posts prepared requests to
SubQ with a key from the environment. No step changes the agent, the
simulator, the prompts or the production code.

Paths are relative to the repository top. Commands use `uv run`; a plain
`.venv/bin/python` works the same. Run the `evaltools` modules from the
`evaluation/` folder or with `PYTHONPATH=evaluation`.

## 1. Produce run evidence

Live runs are Codex's job (AGENTS.md section 12). Whoever runs one should:

1. Record the commit (`git rev-parse HEAD`), the `.env` settings that
   matter (`STEP_QUESTIONS`, `CRITIC*`, `MANUAL_STEP`, models, fallback
   chain), the manual revision and the budgets, in the run's notes.
2. Run with the audit log, so the packet has the full trace:

   ```sh
   uv run python -m capstone.experiment run --name <run> --known --out <run>.jsonl --audit <run>.audit.jsonl
   ```

   or, to also record which functions each case executed:

   ```sh
   cd evaluation && uv run python -m evaltools.traced_run --config ../evals/scenarios.json \
       --name <run> --out <run>.jsonl --audit <run>.audit.jsonl --trace <run>.trace.json
   ```

   The traced runner wraps `capstone.experiment.run_experiment` one case
   at a time under the coverage tracer; the run itself is unchanged.
3. Label the conclusions before looking at any comparison:
   `python -m capstone.experiment label --results <run>.jsonl --labels <run>.labels.jsonl --by <name>`.
   Labels are read from the conclusion's words; the labeller should not
   open the score fields of the same file.

## 2. Build packets

```sh
cd evaluation
uv run python -m evaltools.run_packet --records <run>.jsonl --labels <run>.labels.jsonl \
    --audit <run>.audit.jsonl --commit <sha> --out packets/<run>
# every run of an archived results folder (one subfolder per pair), in one go:
uv run python -m evaltools.run_packet --archive ../docs/benchmarks/2026-11-01-tot13-pairs \
    --out packets/tot13-pairs
```

Each packet is named by its **episode key**, `namespace::run_key`. Archived
pairs reuse every run key, so `--archive` uses each pair's folder name as
the namespace (`--namespace` does the same for one records file), and two
packets with one episode key are refused rather than overwritten. A label
may be a hand label or an auto-label proposal (`{"label", "needs_review"}`);
one that needs review, or that `--review-report` (an eval report) flags
`label_needs_review`, is kept with `label_status: pending_review` and the
run stays unjudged. `BATCH_SUMMARY.json` gives `evals_judged` and
`evals_correct`, the denominators `capstone.evals` publishes (outage runs
included), beside its own reasoning totals (outage runs left out).

Each packet has `meta` (sources, run key, scenario id), `snap_view` (what a
judge may see: an opaque `run_ref`, configuration, trace, code-computed
facts) and `evaluator_only` (truth comparisons). Only `snap_view` is sent;
scenario ids name the fault, so they stay in `meta`. The builder leaves out
(and lists under `refused`) a packet whose judge half carries a truth field
name or the scenario id. Runs where no model answered are asked nothing.
`BATCH_SUMMARY.json` holds the deterministic batch metrics of
`EVALUATION_RUBRIC.md` section 6. Without `--audit` the packet is
`record_only` and most RUN questions are recorded as unknown.

## 3. Build and read the inventories

```sh
uv run pytest --cov=capstone --cov=evaltools --cov-context=test --cov-report= --junitxml=junit.xml
cd evaluation && uv run python -m evaltools.build_inventory --coverage ../.coverage --junit ../junit.xml
```

The repository pins coverage.py's `ctrace` core because the evaluator needs
per-test contexts. On Python 3.14, the default `sysmon` core can lose those
contexts while still reporting passing tests. Rebuild the inventory from a
complete coverage and JUnit run after changing source or tests. Function
packets show at most 80 test sources; when any test is omitted or a source is
cut, FN-02 and FN-03 remain `unknown` in the ledger instead of receiving a
judgment based on incomplete test evidence.

Add or change reviewer judgments in `curated/*.json` (a note for an item
that no longer exists fails the build, so stale judgments cannot linger),
then rebuild. Read `VERIFICATION_MATRIX.json` `counts` first: never
executed, import-only, partial statement coverage, weak assertions, tests
exercising no project function.

## 4. Prepare decision-model requests (dry run by default)

The same questions go to SubQ Snap (`--provider snap`, default), TypeSafe
Jev (`--provider jev`) or both (`--provider both`). In a matched run both
receive the same state, fitted to the smaller budget (28,000 tokens) by
`evaltools.decision_models.fit_state`; `--full-context` sends the whole
state to one provider and makes its answers non-comparable.

```sh
cd evaluation
uv run python -m evaltools.snap_request --out requests/<run> runs --packets packets/<run>
uv run python -m evaltools.snap_request --out requests/fn functions --ids capstone.agent.loop:gather
uv run python -m evaltools.snap_request --out requests/ts tests --ids tests/test_agent_loop.py::test_a_supported_diagnosis_stops_the_test_phase
uv run python -m evaltools.snap_request --out requests/tl tools --names get_readings wait
```

Each `*.request.json` holds the exact `POST /v1/systemone` body (model,
state, up to 16 named questions) and tags: rubric version, commit, question
ids, a digest of the state and a `request_fingerprint` of everything that
decides the answer (provider, model, fitted state, question wording and
criteria, budget, rubric and normalization versions). Files are named
`<provider>_<item>_<fingerprint[:12]>`, so reordering items changes no name.
The judge view is passed through the `SnapView` model (no field it does not
define) and checked, before and after fitting, for truth field names and the
run's own scenario id, run key and episode key; a packet that fails is
written with `body: null` and a `refused: ...` reason. Read them before sending. Questions a packet
cannot answer are listed under `skipped_questions` with the reason. A
packet whose judge view does not fit the evidence budget even after
trimming is written with `body: null` and the reason under `unfittable`,
so one long run never stops the batch; send it alone with
`--full-context` if a single provider's answer is wanted.

To send: `SUBQ_API_KEY=... TYPESAFE_API_KEY=... uv run python -m evaltools.snap_request --provider both --send ...`.
Answers are normalized into `DECISION_ANSWER_SCHEMA.json` as they arrive.
Requests are sent with the project's `capstone.providers.chat.post_json`
(its User-Agent, one deadline per request, errors that name no key). HTTP
429/5xx, timeouts and unreachable services are tried twice more (waiting 2
then 4 seconds). A request that still fails, or fails for good (another HTTP
error, a reply that is not JSON), is written as an answers file with `error`
and no answers, the batch goes on, and the exit status is 1; run the same
command again and only requests without complete answers to the same
fingerprint are sent. An answer outside its question's options or range (a
choice not offered, a noul outside 0–1, a score outside its levels) is kept
with `value: null` and the reason. `compare_evaluators` refuses a folder that
holds two answers to one question of one item, and takes the median latency
over requests, not answers.
Then `uv run python -m evaltools.compare_evaluators --answers requests/<run> --reference reference/<run>.json --out comparison/<run>`
writes the agreement report (`agreement.md`): rates by question, every
disagreement for review, latency, tokens and cost per provider (tokens and
cost counted once per request, since the services report usage per
request, not per question), and each provider's agreement with the
reviewer's answers.
Answers are written beside the requests as `*.answers.json`. Before the
first live request confirm the question shape against docs.subq.ai (the
score-level key is unconfirmed; see `SNAP_QUESTIONS.json` `api`).

## 4a. The whole project in one command

```sh
cd evaluation
uv run python -m evaltools.full_evaluation --commit <sha>     --archive ../docs/benchmarks/2026-11-01-tot13-pairs --out full-eval/<name>
```

A dry run by default: it writes `scope_manifest.json` (every tracked Python
file classed as inventoried, tests, test support, no functions, excluded with
a reason, or unexplained), the packets under `packets/`, every request under
`requests/`, `ledger.jsonl` (one row per item, question and provider with its
status: planned, answered, unreadable, failed, unknown, not applicable, not
run, unfittable, refused) and `report.json` / `report.md`. The report keeps
deterministic correctness per run, the BT-02 sample rule computed in code,
trace completeness, reliability and judging status apart; every figure has
its denominator and there is no blended score. `--commit` must be the
checked-out commit. `--families` limits the plan (`FN,TS,TL,RUN,BT`);
`--provider` picks `snap`, `jev` or `both`. `--send` also needs
`--max-requests` and `--max-usd`. These now limit **new posts in this
invocation** and cumulative spend in the same output folder; `--batch-size`
may set a smaller slice. `--max-seconds` bounds the invocation (600 seconds
by default). The full plan and its pending ledger remain visible. For Snap,
the sender reserves the price of its full 393,216-token input window before
each post, sends once without an automatic retry, then replaces the reserve
with the provider's measured input usage. A failed/interrupted post or reply
without valid usage keeps its reserve and stops later posts, including on
resume. Complete saved replies can settle an interrupted reservation without
posting again. `report.json` and `report.md` show the live spend and stop
reason. Jev/mixed live slices currently stop before posting: Jev's request
window and usage contract still need the small live calibration in Gate C.
Dry runs for either provider still work. The separate `snap_request --send`
command retains its own retry behavior and is not covered by this budget guard.
Snap's [model page](https://docs.subq.ai/using-the-api/models/) lists the
input price and free output; its [Decisions API](https://docs.subq.ai/endpoints/decisions-api/)
states the 393,216-token context limit and usage fields.

## 5. Interpret results

- Report deterministic metrics and judge answers side by side, per case,
  with denominators (`EVALUATION_RUBRIC.md` sections 5 and 6).
- A noul probability is a preference, not calibration: 0.7 / 0.3 are the
  decision lines used for the report, as in `capstone.evaluation.auto_label`.
- Compute the derived flags: misleading success (right and RUN-08 < 2),
  evidence-grounded decision (right and RUN-08 ≥ 3 and RUN-12 ≤ 0.3).
- Validate the judge on the reference set first (rubric section 8). Until
  agreement is recorded, treat judge answers as proposals for review.

## 6. Compare experiments across commits

1. Same scenarios and seeds, same label rule, same rubric version; one
   configuration difference. `capstone.evals --compare-before` refuses
   different scenario sets but not different settings, so check the
   configuration blocks of both `BATCH_SUMMARY.json` files by hand (BT-01).
2. Report differences per case, then totals; apply BT-02's sample rule
   before using the word improvement.
3. Keep both batches' packets and answers; never rescore an old batch under
   a new rubric version without saying so.

## 7. Adding a feature (Phase 9 process)

Before building: write the expected behaviour, the affected functions and
tools (ids from the inventory), the existing tests that may change, the new
tests needed, the observable runtime signs in the record or audit log, and
the success and failure conditions in terms of the rubric's metrics. After
building: rebuild the inventory (new functions appear automatically with
NOT TESTED or PARTIALLY VERIFIED defaults), run the matched cases with
`--audit`, build packets, run the questions, compare with the baseline
batch, and record the result with rubric and context versions.
