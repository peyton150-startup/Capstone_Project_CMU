# Real-Machine Intelligence Acceptance — approved signals to verified diagnostic value

**Repository:** [Capstone_Project_CMU](https://github.com/peyton150-startup/Capstone_Project_CMU) · **Draft PR:** [#233](https://github.com/peyton150-startup/Capstone_Project_CMU/pull/233) · **Scope:** downstream utilization of *authorized, validated* Siemens/DMG MORI machine data in the Manufacturing Research Assistant.

**Status (2026-11-11):** **Documentation only.** Source inspection of `main` and existing synthetic test cases; no code implementation, no new tests executed, no physical Siemens controller qualified and no real OEM benchmark demonstrated. All acceptance requirements below remain **unimplemented / offline-unverified / machine-unverified** unless a future verification record proves otherwise. **Highest-priority P0** for the safe collection→detection→investigation pilot. Real-machine learning/evaluation require subsequent independent technician adjudication.

**Companion normative contract:** [SDC-01–20 Siemens data integrity and acceptance](SIEMENS_DATA_ACCEPTANCE.md). SDC establishes (1) authorization to collect, (2) validity as evidence and (3) eligibility for a downstream consumer. **RMI-01–07 below add the missing consumer-level contracts and end-to-end tests; they do not waive SDC.** The comprehensive [MVP_SCOPE S-0/E2E](MVP_SCOPE.md#fw-real-data-e2e) identifies additional operational requirements. Retain and test existing MTConnect and simulator behavior.

**Product definition:** Detect **developing, subthreshold abnormalities** at comparable production conditions, then provide evidence-based, ranked, technician-checkable root-cause hypotheses. **Do not** replace OEM breakage/overload/collision protection, CNC safety functions, alarms, tool controls, pallet scheduling or maintenance authority. Physical CNC access is **read-only**: no Write, generic Call, file transfer, program changes, alarm acknowledgment, or safety override.

## RMI-01 — All approved signal types and instances are usable **without confusing identity** (P0)

**Target contract:** Introduce a versioned signal catalog independent of `MachineSensor`. Each **approved and actually exposed** signal has unique `facility/source_server/machine/subsystem/nc_channel/axis_or_spindle/tool_or_pallet/native_node/canonical_signal` identifiers; signal class `scalar_numeric | discrete_state | alarm_event | structured | waveform_not_supported`; physical meaning and measured/estimated/derived type; engineering dimension, units and conversion, scale/resolution, coordinate frame, quality policy, update semantics, sensitivities, available consumer capabilities, owner and mapping revision. Represent fan-out of Siemens end-customer vs OEM/PLC servers, multiple spindles/rotary axes, and DMG MORI cell PLCs. **No invention of physically absent data**. A raw node may be allowed to be archived but intentionally not useful to the agent.

**Required APIs (future):** bounded `list_available_signals(machine, as_of, eligibility)`; typed `get_signal_samples(signal_id, start, end, as_known_at, limit)`; `get_signal_summary`, `get_state_transitions` and `get_alarm_events` with full identity/quality/coverage and original lineage; optional cross-signal fetch only after unit/time/state qualifications. Existing numeric tool adapters still work for simulator/legacy MTConnect names. Explicit capabilities for no waveform, insufficient resolution, unavailable source and unauthorized channel.

**PASS:** Same abstract "load" from spindle 1, spindle 2 and X rotary drive remains three independently identified quantities with verified units/semantics; arrays/bitfields/events retain type; only qualified actual capabilities offered. **FAIL:** separate axes collapsed into `load`, a PLC Alarm Condition coerced to numeric, nonfinite or Bad data advertised as available, unknown unit silently guessed.

**Tests (add, not currently passed):** six+ambient legacy regression; Siemens five-axis and dual spindle + integrated PLC topology; same native NodeId on two servers; duplicate named sensors on multiple machines; cyclic multi-item update, arrays, status-only/event data and unknown unit; changed map/firmware; per-signal permission revoked; verified capability list agrees with provider dispatch and absence of control APIs.

**Files affected:** `ingestion/channel_map.py`, `ingestion/record.py`, `contracts/observations.py`, `providers/factory.py`, `providers/replay.py`, `recorded_investigation.py`. **Prerequisite:** SDC-01–07, 12–16, 18. **Status:** specified only.

## RMI-02 — Real, context-conditioned features and baselines (P0)

**Target contract:** A bounded CPU-only feature job consumes *only SDC-17 eligible* observations. Qualified windows carry `machine_id`, source/time/receipt bounds, exact valid duration/coverage, state and cycle phase, qualified RPM/feed/load/power/tool/program/material/environment context **when available and authorized**, map/configuration and feature version, sample/source IDs and gaps. Never compare cutting to rapid, dwell, warmup, tool change, pallet change or another program solely because wall-clock time is adjacent. Confounders that cannot be controlled remain explicit unknowns and block overconfident comparisons.

**Candidate features (implement only when meaningful at actual sampling):** time-weighted and robust mean/MAD/variance; valid extrema and slopes; drift relative to comparable healthy reference; rate of change and sustained-deviation duration; load-vs-RPM/feed residuals; expected-versus-actual axis/drive differences in matched frame/units; cross-source co-occurrence and lag within known clock uncertainty; trend persistence and recovery after a documented change. No artificial acoustic/vibration spectrum without real bandwidth. Distinguish per-sensor effects, baseline insufficiency, machine-wide correlation and single-signal false positives.

**Baseline governance:** Build only from technician-labeled normal windows and held-out later normal periods, with per-machine+version+operation reference IDs, provenance, drift monitors and change-review. Different hardware years/software versions never silently share references. Seven days is an **initial collection goal**, not proof of baseline sufficiency. Feature/window/evidence lineage must survive retention and mapping correction.

**PASS:** known repeated normal cycles score stable with measured coverage; sustained deviation under comparable load/RPM produces a time-bounded, source-traceable candidate with *no invented bearing cause*; missing conditions return `baseline_unavailable`/`insufficient_data`. **FAIL:** simulator healthy reference used in a real machine, held stale values treated as stable, one sample establishes a trend, tool change creates a fault diagnosis, unknown units combined.

**Tests:** state/program/RPM-matched gradual drift, intentional spindle-speed step, ambient-temperature confounder, tool wear versus tool swap, coolant issue vs missing coolant signal, dual-axis drift, sparse/Bad/Uncertain windows, held-out normal false-alert evaluation, baseline version mismatch, synthetic slow failure with multiple causes. **Files:** `tools/screening.py`, `ingestion/time_stats.py`, `ingestion/quality.py`, new real feature engine/baseline registry, monitoring. **Prerequisite:** SDC-05–09, 12, 16–17. **Status:** specified only.

## RMI-03 — Deterministic anomaly-to-investigator bridge (P0)

**Target contract:** The always-on CPU detector emits a **durable, versioned, idempotent incident candidate** only for a persistent quality-supported anomaly. `incident_id`, machine/source identity, `trigger_type` (statistical vs OEM alarm vs operator), first/last valid event time, *as-known receipt cutoff*, trigger feature IDs and source-root IDs, state/context, eligibility and missing coverage, reference/feature/model versions, severity/uncertainty, dedup fingerprint and next-action state are mandatory. The bridge should support `candidate→qualified→queued→investigating→needs_review/closed/abstained` plus updates, coalescing repeated windows and OEM alarm context, and separately identifiable collector-data-quality alerts. **Never** turn every sample into an LLM call.

**Execution:** bounded queue and retry/idempotency, bounded per-machine and site-wide concurrency, controlled cooldown/debounce, explicit delivery acknowledgments, graceful model unavailable/error handling, suppression during irrelevant states, separate human override and operator-initiated investigations. A late alarm from the *same* underlying source may enrich the incident without creating a second root-cause vote. Capture snapshot is immutable for initial triage; later evidence is deliberately labelled post-trigger. No action can alter machine controls.

**PASS:** one persistent load drift with supporting time-window eligibility starts **one** investigation with correct source cutoff, logs missed alerts/queue pressure, and does not launch calls for transient spikes. **FAIL:** every threshold breach triggers duplicate models, state-offline becomes healthy, replay shifts cutoff into future, queue loss silently discards incidents.

**Tests:** short spike vs persistent deviation; restarted detector/replayed notification same incident; 10 coincident signals; OEM alarm alongside detector event; queued delayed incident; recovered source after outage; clock-skewed PLC alarm; no model credentials; model error; operator opt-out; day-long normal synthetic stream; resource usage. **Files:** `monitoring/monitor.py`, `monitoring/runner.py`, `agent/recorded_state.py`, `recorded_investigation.py`; new incident store/orchestrator. **Prerequisite:** SDC-15–18 + RMI-01/02. **Status:** specified only.

## RMI-04 — Real-machine evidence and honest investigation (P0)

**Target contract:** Create explicit `mode=real_machine_triage` with correct industrial terminology, physical time/UTC, no simulated tick/line/job assumptions, and only **actual advertised** capture-backed capabilities. Unify the two recorded entry points into one testable policy/provider/tool specification; preserve the independent CNC read-only boundary. The agent sees **bounded, source-linked** evidence cards showing channel/axis/spindle identity, value/unit/quality, observation time vs receipt time, coverage, operating phase, reference, event lifecycle, origin/source-family and whether it was collected before/after trigger. Show a contrasting comparable healthy window and relevant trend/counterevidence when available. Show unavailable context explicitly; don't fabricate it.

**Retrieval:** with separate shop authorization, use version/serial-matched Siemens and DMG MORI machine manuals, alarm-code references, OEM-approved maintenance/quality and *technician-confirmed* history. Current `SIM-CNC-001` manual must not be presented as applicable to Prestige. Manual/model references are background and never equal observed machine fact. An OEM alarm is context or an already-raised native event—not automatic causal truth. Evidence buffers, prompt/token budget, remote-model permissions, privacy/egress and user-facing recommendations are independently constrained. Unsupported `get_events`, `get_settings`, maintenance/inspection/job data remain honestly unavailable until ingested and authorized.

**Decision thresholds:** report ranked rival causes, observations supporting/contradicting each, confounding variables, unanswered high-value checks, calibration/uncertainty, what a technician should verify first (informational, never commands), and abstention for missing/duplicated/incoherent support. Only claim measured arithmetic if a deterministic code verifier checks actual source, units, time and coverage. A high model confidence is not confirmed diagnosis.

**PASS:** induced synthetic pre-fault trend yields sensor-specific evidence/alternatives and next read-only checks; real mode prompt does not describe a simulator, no synthetic manual/history appears; no physical writes. **FAIL:** unobserved state or alarm invented, current mode mixes 1 tick = simulated minute with physical timestamps, unsupported tool advertised, future data leaked, model follows Siemens alarm text as instructions.

**Tests:** model prompt snapshot in real mode; tool advertising/dispatch parity for supported/unavailable data; exact as-known cutoff under delayed arrival; allowed alarm vs absent alarm; program restricted text; multiple axes and missing unit; authorized matching-vintage manual vs synthetic manual; conflicting evidence/abstention; malicious PLC/alarm message; no Write/Call/Execute tools. **Files:** `agent/model_policy.py`, `agent/evidence_brief.py`, `agent/incident_context.py`, `recorded_investigation.py`, `replay_investigation.py`, `providers/manual.py`/`recall.py`, `providers/replay.py`, `contracts/observations.py`. **Prerequisite:** SDC-07, 10–12, 14, 18 + RMI-01/03. **Status:** specified only.

## RMI-05 — Technician-grounded field learning (P1 for later pilot; P0 specification of safety gate)

**Target contract:** A distinct, versioned **field case/outcome** record captures incident/AI conclusion and evidence, actual shop review, technician role and signoff, verified/unverified/refuted/unknown cause, competing causes, intervention **performed by the shop** (not the AI), service/maintenance evidence, before/after measurement windows, production/tool/program confounders, outcomes including no fault and false alarm, label date, case version, and access/revocation. Never infer successful repair simply from a symptom disappearing after a short idle period.

**Learning gates:** no automatic promotion from AI confidence, no agent self-certification, no simulator "execute_action" on real CNC, no learning a confirmed root cause solely from a tool change that coincided with a symptom change. Separate confirmed fact (root cause), attempted action, observation of improvement and causal uncertainty. Hold corrected, contested, or retracted labels outside active recall; preserve field-case generation/context/revision and prevent cross-machine unqualified reuse. Reuse the existing conservative `MemoryPromotionPolicy`, SQL repository and Chroma only as infrastructure where safe; add a separate independent technician-verification policy and case type instead of relaxing simulator intervention gates.

**PASS:** independently confirmed failing component + documented technician repair + credible independent after-window may become a **qualified** searchable field case with evidence lineage; unconfirmed guess remains an unresolved investigation, not a reusable diagnosis. **FAIL:** triage-only result promoted as proven fix, recollection of AI hypothesis treated as independent confirmation, corrected label survives in active Chroma, confidential machine notes shared across customers without authorization.

**Tests:** confirmed technician case with matching after-measurements; unverified AI conclusion, symptom gone without maintenance, attempted ineffective repair, multiple causes, technician-disputed case, mapping revocation, semantic index/cache retraction, wrong-hardware memory retrieved with "verified" status, sensitive case prohibited to remote model. **Files:** `memory/policy.py`, `memory/contracts.py`, `memory/reflection.py`, `memory/service.py`, `memory/repository.py`, `memory/semantic.py`, `agent/completion.py`, plus future field-case review input. **Prerequisite:** approved labelled outcomes and RMI-04. **Status:** specified only.

## RMI-06 — Independent real-world performance evaluation (P1; release-critical before accuracy claims)

**Target contract:** Field benchmarking is separate from `evaluation/scoring.py` simulator hidden truth and separate from SNAP project-wide software evaluation. Build a **versioned, consented field-event dataset** of healthy/abnormal windows, OEM alarm times, technician-confirmed outcomes and *unknown/censored* periods. Every label carries source/reviewer/reliability/date and potential confounders, and can be corrected. Freeze train/calibration/test chronological splits **before** scoring; prevent leakage of future repair notes, the evaluation label, post-event alarm or a downstream AI answer into upstream detector/LLM context.

**Metrics:** normal false alerts per **eligible operating hour** with clear numerator/denominator and uncertainty; observed alert volume and operator review load; sample→feature→alert→investigation→human latencies (p50/p95 and timeout rate); precursor lead time against OEM-native alarm for cases with both event clocks; top-k cause ranking and checklist utility on confirmed cases; hypothesis evidence support and contradictions; calibration/overconfidence and **false reassurance**; detection precision/recall **only** with an appropriately labelled and observed denominator; stratification by controller/firmware/tool/operation/state and new/old DMG MORI generation. Unknown fault labels are never negatives. No fabricated superiority over OEM monitoring.

**Comparison arms:** (a) existing DMG MORI/Siemens OEM protection/alarms only; (b) our statistical trend detector without LLM; (c) detector + bounded Pydantic AI investigator; optionally (d) operator-initiated investigation. Evaluate what each *adds*, not raw alert count or an internal LLM score. Compare against confirmed technician work and misdiagnoses; report abstentions and missing data separately. Shadow mode remains strictly read-only.

**PASS:** a frozen labelled fixture produces reproducible side-by-side metrics and uncertainty without using unknown cases as false negatives; no pre-alarm lead time claimed on alarm-only/unlabelled cases. **FAIL:** simulator seed truth used to score physical CNC cases, part-program identifiers leaking into test, overlapping repair periods reused across splits, unavailable machine hours counted as healthy, accuracy claimed without real labels.

**Tests:** known positive, censored/unknown label, no OEM alarm, OEM alarm before/after anomaly, no fault positives, cross-serial/version drift, duplicate incidents, denominator with collector downtime, delayed technician label, contaminated split, p95 latency with model timeout, regression of prior baseline and versioned field dataset. **Files:** `evaluation/scoring.py`, `evaluation/labels.py`, `evaluation/known_answers.py` (must remain simulator-scoped), new field benchmark/scorer, `agent/completion.py` and incident store. **Prerequisite:** RMI-01–05 plus independently adjudicated shop cases. **Status:** specified only.

## RMI-07 — Physical-source independence, not just distinct evidence IDs (**P0 diagnostic correctness blocker**)

**Confirmed code-level gap:** `agent/loop.py:diagnosis_supported` currently counts `len(set(leading.supporting_evidence_ids) & observable_ids)` against `min_supporting_evidence` (default 2); it **does not know** whether E1 and E2 derive from one physical measurement. `agent/evidence_brief.py:measurement_groups` groups by `(machine_id, sensor, unit)` and `(tick,value)` and counts some duplicates, but does not preserve a canonical physical-origin lineage. A minute/tick bucket may also collapse same-axis separate samples or conflate two axes under `sensor="load"`. **Existing loop/provenance tests validate ID integrity, not physical independence.**

**Target source-dependency graph:** Every raw observation gets `source_server_id`, `physical_signal_id`, native source/node and `sample_ids/time bounds`; every aggregate/feature derives explicit input sample references and transform/version; OEM alerts, manual, operator review and memory are labelled by evidence *class* and, where observable, originating physical signal/control. Every `Evidence` retains `derived_from` roots, `source_family_id`, whether measured vs derived vs external explanation, and dependency/correlation caveats. Use a reproducible equivalence/dependency closure: identical physical sensor from OPC UA + MTConnect, raw values + trend summary, repeated queries, restated manual explanation or OEM load alarm from **the same underlying sensor** cannot satisfy an "independent confirmations" threshold by multiplying IDs. Two different sensors may be correlated by operation; independence is not guaranteed merely by different node IDs.

**Guardrail design:** Change the *real-machine supported-diagnosis rule* to evaluate source-root **distinctness and evidential relevance**, coverage, confounders, contradicting observations and verified numeric claims. Keep the stored source IDs and E1/E2 evidence IDs for audit; don't break simulator scoring. Treat derived statistical summaries and native OEM alarms as potentially powerful evidence *but not independent copies* of the raw signal. A **single** high-quality source can still trigger an **anomaly candidate**, and an important diagnosis may be reported as **one-source / insufficient confirmation** rather than discarded or claimed supported. Multiple independent signals are not sufficient by themselves to prove a physical cause. If source lineage or OEM derivation is unknown, mark `independence_unknown` and abstain from an independence-based confirmation; don't assume independence. A documented technician inspection can be a separately corroborating source if it is genuinely independent of the claimed sensor.

**PASS:** raw spindle-load E1 + mean-load E2 + load-based OEM alert E3 = **one known physical source family** (unless OEM provenance proves otherwise); no automatic 3-source diagnosis support. A verified independent temperature sensor or technician-confirmed observation can be additional *distinct* supporting evidence when truly independent and causally relevant. **FAIL:** confidence raised because one source was represented in three formats, two server aliases reported as separate measurements, or "unsupported" claim from absent sensor.

**Required tests:** (1) raw + summary + OEM-derived alert same source; (2) same measured value through Siemens OPC UA and DMG MORI MTConnect; (3) correlated X/Y servo load from one shared common operating state (not assumed independent causal support); (4) distinct measured spindle vibration vs verified bearing temperature plus confounder; (5) repeated query/cache or late delivery with new E-ID; (6) same minute two genuinely different samples preserved; (7) missing physical lineage ⇒ unknown/not confirmed; (8) independent technician inspection with original source; (9) deliberately conflicting independent reading forces unresolved/recheck; (10) simulator scoring and existing evidence IDs unaffected.

**Files:** `agent/loop.py:diagnosis_supported`, `agent/evidence_brief.py:measurement_groups`, `contracts/evidence.py`/`contracts/provenance.py`, `providers/replay.py`, new canonical provenance and dependency evaluator. **Prerequisite:** SDC-03/04/07/12/14/18 + RMI-01/04. **Status:** specified only.

|---|---|---|---|
| **R0** | SDC-01–20 + RMI-01 | Authorized installed machine/option/source topology, versioned approved signals and typed tested physical identities; no unauthorized reads/writes | **Yes** |

**Mandatory cross-stage fixture:** One machine with approved spindle RPM/load, axis-drive current, independent temperature, operating transitions and a native alarm; a second machine/PLC with overlapping NodeId; a gradual load trend during comparable cutting; a tool/pallet change; Uncertain/Bad status and a reconnect; a delayed alarm; a duplicate MTConnect/OPC UA view; an operator-confirmed later inspection/repair; one read-only agent conclusion. Follow each approved source from original type/quality/time through normalization and missing coverage, state segmentation, feature, incident, immutable as-known snapshot, agent's E-IDs and evidence roots, human adjudication, memory decision, and field evaluation. Verify no future information, source collision, unsupported or unauthorized data, controller action, causal overclaim, or unapproved LLM egress.

**Negative fixture:** A corrupted source with denied permissions, no valid baseline, duplicate physical evidence and a malicious alarm message **cannot** lead to a supported root-cause verdict or a healthy assertion; it produces explicit insufficient-evidence / source-failed state, and no CNC call.

**Definition of done (documentation):** Every RMI-01–07 has: existing module link, target contract, signed requirements owner when assigned, dependency/actual machine applicability, explicit PASS and FAIL behavior, positive+negative regression cases, test evidence artifact and `documented | implemented | offline_verified | machine_verified | blocked` status. The same is true of applicable SDC-01–20. **No current code/tests are claimed to satisfy real-machine release gates by this requirements file.** Mark each future case when a reproducible offline test and separately authorized machine validation actually pass.
