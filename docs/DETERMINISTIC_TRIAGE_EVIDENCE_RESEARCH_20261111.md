# Simulator-first deterministic triage evidence gathering — research and exhaustive signal/noise options

**Status:** RESEARCH / PROPOSED ONLY, 2026-11-11. **No runtime, setting, model or Siemens behavior is implemented by this document.** Discuss and select candidates on 2026-11-12 before beginning any coding PR. This is a *separate workstream* from the 36-item Siemens/production signal-ranked queue in `SIGNAL_PRIORITY_IMPLEMENTATION_ROADMAP_20261111.md`; its relative HIGH/MEDIUM/LOW judgments do not change that queue's exactly-two-HIGH rule or any mandatory P0 Siemens SDC/RMI gates.

**Immediate scope:** controlled simulator ONLY; improve the relevance, distinguishability and provenance of *observable* evidence delivered to existing triage, with deterministic Python selection. Preserve the current 90-second triage budget and the existing iterative triage as the control. Do **not** modify the full/deep investigation yet. A future optional `TRIAGE_STRATEGY=evidence_first` remains a design proposal, **not** an existing setting. Do not start physical Siemens ingestion or assert that simulator reference values describe a real machine.

## Code-grounded starting point and the problem

- `capstone-code/capstone/tools/screening.py`: `make_reference` produces a separate fault-free 8-machine, 2,880-tick healthy reference; `build_ranges`, `score`, `screen_machine`, `screen_line` compare running observations to machine/sensor and temperature warm-up reference statistics. `compact` intentionally reduces prompt size. `tools/healthy_reference.json` and `tests/test_line_screening.py` exist and are tested.
- `capstone-code/capstone/tools/observation.py:get_line_screening` exposes the simulated scores. `agent/investigation.py:observe` gathers them **after** a triage has already been triggered, when screening is available.
- `capstone-code/capstone/agent/monitor.py:detect_anomaly` currently triggers from simulated alarm/status events, failed inspections or routine checks; **it does not initiate episodes from the statistical scores**. The healthy-reference comparison is an existing *screen*, not yet an always-on scored-incident trigger.
- `agent/incident_context.py` conditionally collects a bounded line packet; `agent/loop.py:gather` already records observable tool evidence IDs. Reuse these foundations; do not create another generic agent, another simulator baseline or an unrelated data platform.
- Distinguish (1) **detection/onset recall** before triage, (2) **diagnostic evidence recall/isolability** after a trigger, and (3) **LLM diagnosis quality** from the evidence packet. Optimizing only the 90-second model time can conceal missed or late anomalies.

### Rejected noise — **not** added as implementation backlog

1. **Another generic LLM agent or framework** to gather evidence: additional latency and overlapping responsibilities. Python can handle bounded selection; keep Pydantic Graph control.
2. **Active tests that change machine settings or physically excite a CNC**: some sensor-selection papers optimize input manipulation; this violates the initial read-only real-machine scope and is unnecessary for simulator evidence collection. Offline simulation experiments are permitted but **not** runtime actions.
3. **Full deep neural causal graph / CF-LSTM as an immediate dependency**: disproportionate data/computation/validation burden until simpler signatures and temporal evidence fail. S13 is research context, not an endorsement to implement LSTM.
4. **Treating simulator fault labels or saved hidden-health fields as runtime evidence**: ground-truth leakage invalidates the comparison.
5. **Uploading raw shop telemetry or building a universal Siemens baseline**: unrelated to simulator-first evidence packet and prohibited without qualifying real-machine data and approval.
6. **Promising a verified mechanical root cause or repair after one LLM call**: a bounded first diagnosis can be useful, but unobserved checks and post-intervention validation remain unresolved.

## Proposed simulator-only experiment / acceptance gate

**Phase A — baseline (do first).** Freeze the existing `triage` (90 s), `screen_line` and `detect_anomaly` behavior and seed set. Generate fault-free healthy references from a separate run only. Record fixed evidence gather and existing agent on single fault, decoy-first KA-09, wrong-setting, gradual wear, normal/false alarm, missing/delayed/stale telemetry, sensor drift, changing operating state and two simultaneous causes.

**Phase B — deterministic packets without model reasoning change.** Produce an opt-in packet using read-only provider tools, including: event/trigger and cutoff; line screening and all-machine status; target and neighbor histories with signed magnitude, change window and eligible operating state; specific contradictory alternatives; absent/unavailable channels; raw-to-feature physical source lineage; unique evidence IDs. Every row must be reproducible and match the time cutoff; **no ground-truth imports**. Leave the LLM investigation stages unchanged for the first paired benchmark.

**Phase C — selection comparison.** Compare (1) current post-trigger screening + existing agent, (2) fixed deterministic packet + existing agent, (3) fault-signature selection + same agent, and (4) information-gain sequential selection + same agent. Only after a measurable improvement may a *separate* one-model-call `TRIAGE_STRATEGY=evidence_first` be considered; do not modify deep mode or the critic in this research PR.

**Metrics (report by fault severity and case type):** true-positive and false incident triggers; detection delay from independently labelled onset; fault-relevant evidence recall@budget; pairwise fault isolability / distinguishing-observation coverage; supporting **and contradicting** observable source-family recall; wrong-machine selection; multi-fault coverage; fraction of packets missing required evidence; abstention/false confident no-action; p50/p95 evidence gather and complete triage time; model calls, tool calls, prompt characters and tokens. Avoid claiming diagnosis metrics from a feature-only run.

**Acceptance rule:** no hidden-truth leak, no write/action, 90-second triage limit retained, missing data never counted healthy, no worse missed serious fault/false clearance at a predeclared tolerance, and meaningful measured gain over the fixed baseline. Reject complexity if performance is tied or unstable across held-out seeds. Missing independent labels -> inconclusive, not passed.

## Verified papers (relevance and external validity)

S1. Moliner-Heredia et al. (2021), [**A Sequential Inspection Procedure for Fault Detection in Multistage Manufacturing Processes**](https://doi.org/10.3390/s21227524). **New top research addition:** information-gain-ranked sequential reads after monitoring for multistage manufacturing. Manufacturing-relevant, but field validations still differ from our simulated CNC.
S2. Kościelny et al. (2016), [**Fault isolability with different forms of the faults–symptoms relation**](https://doi.org/10.1515/amcs-2016-0058). Fault-signature / symptom sequence distinctions.
S3. Lucke et al. (2019), [**Variable selection for fault detection and identification based on mutual information of alarm series**](https://doi.org/10.1016/j.ifacol.2019.06.140). Alarm-series variable selection validated on a multiphase flow facility, not a CNC.
S4. Peng, Long, Ding (2005), [**Feature selection based on mutual information: criteria of max-dependency, max-relevance, and min-redundancy**](https://doi.org/10.1109/TPAMI.2005.159). General feature selection, not domain-specific fault isolation.
S5. Lucke et al. (2020), [**Fault detection and identification combining process measurements and statistical alarms**](https://doi.org/10.1016/j.conengprac.2019.104195). Alarms + raw measurements, two alarm severity levels; industrial flow context.
S6. Lucke et al. (2020), [**Integration of alarm design in fault detection and diagnosis through alarm-range normalization**](https://doi.org/10.1016/j.conengprac.2020.104388). Use alarm-range scales as a different normalization source; process plant, not CNC.
S7. [**Variable Selection for Fault Detection Based on Causal Discovery Methods: Analysis of an Actual Industrial Case**](https://doi.org/10.3390/pr9030544) (2021). Conditional-dependence selection, benchmark and oil/gas case.
S8. [**Lag-Specific Transfer Entropy for Root Cause Diagnosis and Delay Estimation in Industrial Sensor Networks**](https://doi.org/10.3390/s25133980) (2025). Propagation ordering / source candidate; directional information is not proof of causation.
S9. [**Sensor selection for fault diagnosis in uncertain systems**](https://doi.org/10.1080/00207179.2018.1484171) (2018). Sensor noise and fault distinguishability.
S10. [**Optimal sensor selection for active fault diagnosis using test information criteria**](https://doi.org/10.1016/j.ifacol.2019.06.092) (2019). Noise/sensitivity-aware sensor choice; omit physical input-manipulation component.
S11. Awasthi et al. (2020), [**Optimal test and sensor selection for active fault diagnosis using integer programming**](https://doi.org/10.1016/j.jprocont.2020.06.007). Information-theoretic sensor/test ranking with model uncertainty; optimization complexity and input intervention are not first-pilot candidates.
S12. Kościelny and Sztyber-Betley (2025), [**Definitions and comprehensive assessment of fault isolability in expert-based diagnostic systems**](https://doi.org/10.1016/j.ymssp.2025.112979). Rigorous conditional and sequence-based isolability measures, with research code; more complex than needed initially.
S13. [**Hierarchical Causal Graph-Based Fault Root Cause Diagnosis and Propagation Path Identification for Complex Industrial Process Monitoring**](https://doi.org/10.1109/TIM.2023.3268464) (2023). Contribution screening + hierarchical causal analysis + neural propagation; hot-strip-mill context, more expensive and data-intensive.
